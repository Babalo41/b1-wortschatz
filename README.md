# B1 Wortschatz

Offline-capable PWA for learning the full Goethe-Zertifikat B1 vocabulary
list (~2,991 entries extracted from the official Wortliste PDF, pages
16–102 — see "Why 2,991 and not ~2,400" below).

## Project structure

```
Goethe-Zertifikat_B1_Wortliste.pdf   Source PDF (gitignored -- copyrighted;
                                      keep it locally to re-run extraction)
data/words.json                      Extraction output (source of truth)
src/data/words.json                  Copy bundled into the app build
scripts/extract.py                   PDF -> data/words.json
scripts/inspect_page.py              Debug helper: dump raw word positions for one page
scripts/check_layout.py              Debug helper: x0 histograms across pages
src/lib/german.js                    Verb conjugation / noun declension engine
src/lib/german.test.js               Unit tests for german.js (vitest)
src/lib/words.js                     Loads words.json, assigns ids, gender colors
src/lib/db.js                        IndexedDB wrapper: Leitner progress, streak
src/lib/filters.js                   Shared filtering logic (letter/pos/box/etc.)
src/lib/tts.js                       speechSynthesis wrapper (iOS voice-load quirk handled)
src/components/                      React components (WordCard, LearnMode, TestMode, ...)
public/icons/                        PWA icons (generated, see below)
vite.config.js                       Vite + vite-plugin-pwa (manifest, service worker)
.github/workflows/deploy.yml         Build + deploy to GitHub Pages on push to main
```

## Re-running extraction

Requires Python 3 with `pdfplumber` (`pip install pdfplumber`).

```bash
npm run extract
```

This runs `scripts/extract.py` against the PDF and copies the result into
`src/data/words.json` so the next `npm run build` picks it up. The script
prints a verification summary (entry counts by part of speech, verb/noun
completeness, any suspicious long plural codes) — check that output before
trusting a re-extraction.

**Known limitations of the extraction** (see full discussion in the Phase 1
conversation): ~1.3% of verbs have malformed principal parts (impersonal
verbs, multi-word infinitives like "spazieren gehen"), a handful of
examples get truncated when one entry's multi-line example visually lands
on the exact PDF row where the next headword starts, and a few heavily
cross-referenced entries (regional variant chains) come out garbled. None
of this is silently dropped — it's all still in `words.json`, just
imperfect on those specific entries.

### Why 2,991 entries, not "~2,400"

The Goethe-Institut's own "~2,400 words" figure is a rounded lexical-unit
count. The literal PDF has more *rows* than that: every regional
cross-reference pair (Altenheim ↔ Altersheim), every gendered pair
(Autor/Autorin), every homograph (die Bank *bench* vs. die Bank *financial*)
is its own row, and per the extraction spec these are intentionally not
deduplicated. Verified by hand-counting entries on rendered PDF page
images against extractor output (pages 16 and 17 matched exactly).

## Adding or correcting a word

Words live in `data/words.json` (and its copy in `src/data/`). Each entry:

```json
{
  "head": "abfahren",
  "pos": "verb",
  "gender": null,
  "plural": null,
  "verb": { "p3": "fährt ab", "praet": "fuhr ab", "partizip": "abgefahren", "aux": "ist" },
  "reflexive": false,
  "region": null,
  "examples": ["Unser Zug ist pünktlich abgefahren."],
  "page": 16
}
```

To hand-correct one entry: edit it directly in both `data/words.json` and
`src/data/words.json` (or edit `data/words.json` and re-run
`node -e "require('fs').copyFileSync('data/words.json','src/data/words.json')"`).
To add a brand-new word not in the PDF: append an entry with the same
shape; `id` is assigned automatically at load time
(`page|pos|head|plural|index`), so you don't need to set one.

The conjugation/declension engine (`src/lib/german.js`) only needs
`head`, `pos`, `gender`, `plural`, and `verb.{p3,praet,partizip,aux}` —
grammar is never generated by a model, only derived from these seed facts
plus regular German rules.

## Deployment (GitHub Pages)

Pushing to `main` triggers `.github/workflows/deploy.yml`, which runs the
test suite, builds with the correct `/repo-name/` base path, and deploys
to GitHub Pages automatically. To do it manually:

```bash
git add -A
git commit -m "your message"
git push origin main
```

Then check the Actions tab on GitHub for the deploy run; the Pages URL is
shown in the workflow's "deploy" job summary once it finishes (looks like
`https://<username>.github.io/<repo-name>/`).

### Installing on iPhone (no laptop needed after the link exists)

1. Open the deployed URL in **Safari** on your iPhone (must be Safari, not
   Chrome — "Add to Home Screen" installs as a real PWA only from Safari).
2. Tap the **Share** button (square with an up arrow) in the toolbar.
3. Scroll down and tap **"Add to Home Screen"**.
4. Tap **Add**. An app icon appears on your home screen.
5. Open it from the home screen icon (not from Safari) — it now runs in
   standalone mode, full-screen, and works with **no network** after this
   first load (the service worker has cached everything, including the
   full word list).

### Pushing updates without losing your progress

Your Leitner progress (box, due dates, streak) lives in **IndexedDB**,
scoped to the deployed origin (`https://<username>.github.io`), not to any
particular build. As long as you keep deploying to the *same* GitHub
Pages URL:

1. Make your changes, commit, push to `main` (or re-run extraction first
   if you changed `data/words.json`).
2. The Actions workflow rebuilds and redeploys automatically.
3. Next time you open the installed app, the service worker
   (`registerType: "autoUpdate"`) detects the new build in the background
   and activates it on the next launch — your IndexedDB progress is
   untouched, because updating the app doesn't clear browser storage,
   only `resetProgress()` in the Dashboard does that (with a confirmation
   prompt).

The one thing that *would* wipe progress: deploying to a **different**
domain/path (e.g. renaming the repo, which changes the Pages URL) — that's
a different origin as far as the browser's storage is concerned.

## Design notes

- **Leitner over SM-2** for spaced repetition: simpler fixed-box model,
  no ease-factor tuning, easy to show as a progress bar. Full rationale in
  a comment at the top of `src/lib/db.js`.
- **Vanilla-Vite-React, minimal dependencies**: `react`, `react-dom`,
  `idb` (thin IndexedDB wrapper) at runtime; `vite`, `@vitejs/plugin-react`,
  `vite-plugin-pwa`, `vitest` for tooling. No state-management library,
  no UI kit, no router (three tabs are plain state).
- **Grammar is never model-generated.** Article, plural code, and verb
  principal parts come straight from the PDF; `german.js` only derives the
  regular, rule-governed forms (the other conjugated persons, declined
  noun cases) from those seed facts.
